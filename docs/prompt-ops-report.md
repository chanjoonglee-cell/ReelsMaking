# 🧪 Prompt Ops 1차 리포트 — 원어민 변환 프롬프트 최적화

> **작성일** 2026-06-04 · **담당** 이찬중 · **과제** 6월 1주차 AX 컨설팅 — Prompt Ops
> **대상 프롬프트** 한국어 일기 → 원어민 영어 변환 (speaking)

## ⚡ TL;DR (한 줄 요약)

진단표 기반으로 변환 프롬프트를 개선해 **품질 +11.7점(81.3 → 93.0)** 을 실측으로 입증했고, 그 과정에서 **현재 운영 프롬프트(v1)의 응답 누락 버그**까지 발견했다. 경량화 버전(v1.2)은 품질을 유지하면서 프롬프트를 ~30% 단축했다.

---

## 1. 무엇을 / 어떻게 했나

- **자산:** 진단표(실패 패턴 5종) + 정답셋 20건(TASK4) + LLM 채점 하니스(`run_eval.py`)
- **방법:** 정답셋 20건을 GPT-4.1로 변환 → 6개 축(opener·시제/상·명사화·강조·자연스러움·형식)으로 자동 채점 → 평균 비교
- **비교군:** `v1`(현행 운영) vs `v1.1`(진단 반영 개선) vs `v1.2`(v1.1 경량화)

## 2. 결과 (실측, GPT-4.1, n=20)

| 버전 | 전체 20건 | held-out 17건 (오염 제외) | 비고 |
|------|-----------|---------------------------|------|
| **v1** (현행) | 81.3 | 81.1 | 기준선 |
| **v1.1** (개선) | **93.0** | 92.2 | 최고점 (단, 길고 일부 오염) |
| **v1.2** (경량) | 90.8 | 91.2 | 동급 품질 · 프롬프트 30%↓ |

→ **공정 비교(held-out) 기준 v1.1 ≈ v1.2 (92 vs 91, 통계적 무승부).** v1.1의 표면 우위는 대부분 eval 오염 때문.

### 유형별 평균

| 유형 | v1 | v1.1 | v1.2 |
|------|----|------|------|
| emphasis (강조) | 81 | 97 | **98** |
| baseline | 67 | 94 | 94 |
| tense (시제·상) | 86 | 90 | 90 |
| nominalization (명사화) | 85 | **92** | 82 |
| opener | 85 | 100\* | 75 |

\*opener는 표본 1건 + 오염이라 신뢰도 낮음

---

## 3. 핵심 발견

1. **개선은 실증됐다 (+11.7점).** 진단한 약점(강조 81→97, baseline 67→94)을 정확히 타격. 무작위 개선이 아니라 타깃 개선.
2. **🚨 현행 프롬프트(v1)에 운영 버그.** 한 케이스에서 v1이 번역 대신 *"Sure! Please provide the original text…"* 라고 되물어 **0점**. v1 구조가 입력값 `<original>`을 [역할]에 묻어둬 모델이 가끔 입력을 인식 못 함. **라이브 유저가 가끔 빈/엉뚱한 응답을 받고 있을 수 있음** (→ #feedback "잘 안돼요"의 유력 후보). v1.1/v1.2는 `#입력문` 슬롯 분리로 해결됨.
3. **"짧게 = 항상 좋음"은 거짓.** v1.2(30% 단축)가 명사화에서 살짝 흘림(92→82). 측정 없이 줄였으면 못 봤을 손실.
4. **Eval 오염 발견.** v1.1 예시 3개가 정답셋과 동일 → 해당 케이스 점수 부풀려짐(예: 케이스 1에서 v1.1=100 vs v1.2=75). **예시와 정답셋은 분리** 원칙 확립.

| v1.1 | 93.0 | 91.5 | |
| v1.2 | 90.8 | **92.1** | 2차 최고점 (18/20) |

### ★ 핵심 교훈 (변동성)

- **단일 실행은 노이즈가 크다.** 생성 `temperature=1` + 채점 LLM 변동 때문에, *같은 프롬프트*도 실행마다 ±2~7점 흔들린다. (반복한다고 점수가 점점 오르는 게 아니라, 무작위로 bounce.)
- **v1.1 / v1.2 / v1.3 은 90~92 사이 동점(통계적 무승부).** v1.2 이후의 "최적화"는 노이즈 바닥에 닿아 더 이상 안정적 향상이 없다.
- **v1.3(복잡도↑)은 v1.2를 못 이겼다** → 측정 이득 없는 복잡도는 추가하지 않는다. (좋은 멈춤 신호)

### ✅ 최종 결론 / 운영 추천

- **의미 있는 격차 = 현행 v1 구조 vs 개선군.** 개선군은 응답 누락 버그가 없고 안정적.
- **운영 투입 1픽 = `v1.2`** — 2차 최고점(92.1·18/20) + **가장 짧음(토큰·비용↓)** + eval 오염 없음.
- 더 정밀히 보려면: *다회 실행 평균* 또는 *생성 temp=0*. (현 단계엔 과함 — 여기서 종료가 합리적)

## ⚡ 부록 — Latency(응답 속도) 측정 & 운영 모델 추천

**측정:** v1.2 프롬프트(speaking)를 4개 모델에 동일하게 돌려 **품질 + 지연** 동시 측정 (정답셋 20건, 채점기는 `gpt-4.1` 고정). 재현: `~/prompt_ops/run_latency.py` · `results_latency.json`

| 모델 | 품질 | avg | **p95(꼬리)** | 판정 |
|------|------|-----|---------------|------|
| gpt-4.1 (현행) | 90.5 | 0.86s | 1.64s | 기준 — 가끔 느려짐 |
| **gpt-4.1-mini** | 89.8 | 0.71s | **0.85s** | ★ 품질 동급 + 꼬리 반토막 |
| gpt-4o | 88.2 | 0.58s | 0.89s | avg 최速이나 품질 −2 |
| gpt-4o-mini | 87.2 | 0.80s | 1.42s | 품질 최저 + 안 빠름 = 탈락 |

### 핵심 발견

1. **속도 이득이 1.1~1.5x로 작다.** 출력이 1줄이라 지연 대부분이 고정 오버헤드(TTFT/네트워크) → 생성 토큰이 적어 모델을 줄여도 깎을 게 적음. (모델 다운사이징의 한계)
2. **avg보다 p95(꼬리 지연)가 중요.** gpt-4.1은 가끔 1.64s까지 튐. mini·4o는 0.85~0.89s로 일관. 유저 체감은 "최악 대기"가 좌우.
3. **gpt-4o-mini는 함정** — 품질 최저인데 빠르지도 않음. 후보 탈락.

### ✅ 운영 모델 추천 = `gpt-4.1-mini`

- 품질 89.8 vs 90.5 → **−0.7점 = 노이즈 안쪽(사실상 동급)**
- **p95 1.64s → 0.85s (거의 반토막)** = 느린 케이스 제거
- 같은 4.1 패밀리 → 동작 일관 + **비용도 더 저렴** (속도·품질·비용 동시 이득)
- *절대 avg가 더 급하면* `gpt-4o` (품질 −2 감수)

### 더 큰 latency 레버 (아키텍처 — 하니스 측정 밖)

- **멀티콜 병렬화:** 변환·채점·피드백·대안이 *순차 호출*이면 유저는 합산 시간을 대기. 독립 호출은 동시에(`asyncio`) → 모델 교체보다 큰 효과 가능.
- **스트리밍:** 1줄 출력이라 첫 토큰만 빨리 떠도 체감 지연 크게↓ (총 연산시간은 동일).
